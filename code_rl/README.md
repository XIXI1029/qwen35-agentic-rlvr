# Code RLVR 实验（第二个可验证任务）

> 与主项目（数学 GSM8K）**同一条 RLVR 流水线**，只把"可验证奖励"从"比数字"换成"跑代码测试"。
> 目的：证明这套 GRPO+RLVR 流水线**与任务无关、可迁移**——这是回应"小学数学题没有业务价值"质疑的最直接证据。

## 和数学实验的对应关系

| | 数学实验（项目主目录） | 代码实验（本目录） |
|---|---|---|
| 训练题库 | GSM8K（题面+数值答案） | **MBPP**（题面+隐藏 assert 测试）|
| 评测 | GSM8K / AIME2024 | **HumanEval pass@1** |
| 奖励判定 | `scripts/verifier.py` 比数字 | `code_rl/code_verifier.py` 沙箱跑测试 |
| 训练入口 | `scripts/run_grpo.py` | `code_rl/run_grpo_code.py` |
| 产物 | `outputs/qwen3.5-4b-grpo` | `outputs/qwen3.5-4b-grpo-code` |
| 一键 | `run_full_pipeline.sh` | `code_rl/run_code_pipeline.sh` |

两者**共用**：模型加载/LoRA/冻结视觉（`scripts/model_utils.py`）、环境与镜像（`scripts/_bootstrap.py`）、汇总表（`scripts/compare_models.py`）。

## 一键运行

```bash
# 服务器上（建议 nohup 挂后台）
CODE_MAX_STEPS=300 nohup bash code_rl/run_code_pipeline.sh > code_rl/logs/code.log 2>&1 &
tail -f code_rl/logs/code.log
```
流程：建题库 → Code-GRPO 训练 → HumanEval 评估（Base / SFT起点 / Code-GRPO）→ 汇总到 `outputs/results/SUMMARY.md`。
断点续跑：中断后重跑同一条命令，已完成的步骤自动跳过；GRPO 从最近 checkpoint 续训。

## 沙箱说明（**认真看**）

`code_sandbox.py` 是"T1 受限执行"，护栏：
1. 子进程隔离 + 硬超时（超时判错并 kill 整个进程组）
2. 资源限制：CPU 时间 / 内存 / 文件大小 / 进程数（Linux `rlimit`；Windows 退化为仅超时）
3. 断网：runner 里把 `socket` 换成抛错的桩
4. 独立临时目录，用完即删；输出体积截断

⚠️ **它挡不住**刻意的提权/内核漏洞利用。请：
- **不要用 root 跑**长时间训练（用普通用户）；
- 有条件就放进容器（Docker/nsjail）里跑；
- 这是研究与自建数据集场景的取舍，不是生产级判题系统（生产用 Judge0 / EvalPlus 那套）。

## 文件清单

| 文件 | 作用 |
|------|------|
| `code_sandbox.py` | T1 沙箱：提取代码、受限执行、并行批量（含自测 `python code_sandbox.py`）|
| `code_verifier.py` | Code RLVR 奖励函数（TRL 接口，内部并行跑沙箱）|
| `build_code_pool.py` | 构建 MBPP 训练题库 / HumanEval 评估题库（统一 `{prompt, ground_truth}` 格式）|
| `run_grpo_code.py` | Code-GRPO 训练（复用主项目全部训练零件）|
| `evaluate_code.py` | HumanEval pass@1 评估（结果并入 `outputs/results/`）|
| `code_config.yaml` | 训练/沙箱配置 |
| `run_code_pipeline.sh` | 一键（可断点续跑）|

## 预期与预算
- 代码生成比数学长（每题 ≤320 token），**每步还多一次沙箱执行开销**，所以比数学实验慢；
- 单卡建议先 `CODE_MAX_STEPS=200~300` 跑通看趋势，再决定加量；
- 参考：4B 模型 HumanEval pass@1 起点通常个位数~十几个百分点，RL 后有可见提升即为有效信号（代码 RL 提升幅度一般小于数学）。

## Key takeaways
1. **The GRPO+RLVR loop is task-agnostic**: math compares numbers, code runs unit tests — only the reward function and question pool change.
2. **The hard part of code rewards is safety and stability, not the algorithm**: without hard timeouts, resource limits and network isolation, an infinite loop generated by the model can hang training.
3. The same recipe applies to any task whose correctness is programmatically checkable (NL2SQL result-set comparison, field-level extraction, API-call validation).
